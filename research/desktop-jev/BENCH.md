## 4. 修掉的坑：τ 的语义在部署侧丢了

- 现象：`calibration.json` 的 τ=0.5 是在**等张校准后**的 conf 上选出来的，
  但文件里没存等张映射，`serve.py` 拿**原始 sigmoid** 去比 τ。
- 后果：离线「覆盖率 70.9%」在线上根本不是那个数，升级率/VLM 调用数全部失控。
- 修法：`calibrate.py` 落盘 isotonic 断点 → `serve.py` 用同一套分段线性插值；
  `calibration.json` 里没有 isotonic（旧 ckpt）时如实回退原始 conf，并用 `confidence_raw` 保留诊断值。
- 同时把留出集**按轨迹文件再分半**：一半拟合温度/等张，一半只选 τ + 报 ECE
  （原实现同批拟合+评估，ECE=0.0 是假象）。
- 旧 ckpt 重校准结果：`temperature_op 0.7 / temperature_elem 0.8 / τ 0.77 /
  覆盖率 0.759 / 风险 0.069 / ECE 0.095→0.067（选择集）`。

## 6. 观测成本攻坚（首测后立刻做的一件事）

**体检结果**（`scripts/measure_observe.py`，本机实测，纯只读）：

| 项 | 值 |
|---|---|
| UIA 枚举总耗时 | **0.97–1.6 s/次**（前台窗口 + 后台窗口 DFS） |
| 访问节点 | 437 个（预算 3000，远没到顶） |
| 产出元素 | 51–56 个 |
| 顶层窗口收集 | 133 ms |
| **两个无关后台窗口** | 音乐播放器 ~240 ms + Alienware 控制中心 ~280–450 ms（**占 86%**） |
| 前台窗口（终端） | 47 节点 / 53 ms |
| 截图 + SoM + JPEG | ~120 ms（比枚举便宜得多） |

根因：`uiautomation` 的 `GetChildren()` 是 `GetFirstChild → GetNextSibling` 逐节点走，
每个节点还要读 `ControlTypeName`/`BoundingRectangle`；慢 provider 每节点 ~4 ms 的跨进程
COM 往返。**节点数不是瓶颈，每节点成本才是。**

试过四条路：

| 方案 | 结果 | 结论 |
|---|---|---|
| ①多窗口并行遍历（线程各自 CoInitialize + 认领窗口） | 1.49 s vs 串行 1.52 s，元素表完全一致 | **无收益**，已回退（UIA 跨进程调用在 broker 侧仍串行） |
| ②枚举时间预算（前台不限时 + 后台按历史成本从便宜到贵走，超时即停） | 400 ms → 观测 0.55 s / 27 元素；150 ms → 0.18 s / 17 元素 | **有效但有代价**（元素表变短），做成开关 `SCREEN_USE_UIA_BUDGET_MS`，**默认 0=不限** |
| ③升级步复用刚枚举的元素表（`screenshot(elements=...)`） | 每次升级省一整轮枚举（0.5–1.5 s），零风险 | **已默认开启**（`metrics.enum_reuse` 计数） |
| ④**后台窗口元素表缓存**（句柄+标题+矩形命中且未过期 → 复用；前台每步重走） | 冷启 326 ms → 热 **153 ms（2.1×）**，复用 3 个后台窗口，**元素表不缩水**（70→70） | **已默认开启**（`SCREEN_USE_UIA_WINDOW_CACHE_TTL_S`，默认 2s，0=关） |

④ 的安全阀（要动点击路径，所以特意做了两层）：
- 点/写之前用 `element_still_valid()` 读一次**实时 bbox**，与缓存比对（±4px 容差）；
- 不一致或控件已失效 → 清缓存 → 全量重枚举 → 按 (名称, 类型, 最近位置) 重新解析同一个控件；
  再找不到就**明确报错**（交给上层重新观察），绝不按旧坐标点下去。

补充（2026-09-19 当天复测）：那波 1.4 s 的病理后来消失了——ACC 关掉后同一台机器降到 ~0.1–0.2 s，
说明**慢 provider 是随应用/状态的，不是常驻**。缓存的价值不只是平均值，而是**免疫**这种回归：
常驻慢窗口一旦出现，热路径不再为它付费。

## 7. mock→real 泛化首测（R4）：真实域覆盖率 10% → 门控后 0%

用已攒下的真实轨迹（`~/.screen_use/traces_full`，9 个任务 / 76 条可训样本）量了一次**真实域**指标
（`scripts/eval_offline.py --data traces_full`）：

| 域 | 样本 | 元素数中位 | token 中位 | op_acc | joint_acc | 升级率 | Jev 时延 p50 |
|---|---|---|---|---|---|---|---|
| mock（训练域） | 3100 | **14** | **457** | 0.98 | **0.77** | 0.24 | 40 ms |
| real（计算器/记事本） | 76 | **84**（最大 107） | **2380** | 0.64–0.85 | **0.17** | **0.90** | **452 ms** |

三条结论：

1. **泛化崩塌的主因是观测尺度，不是措辞**：真实桌面的元素表是训练集的 6 倍长、token 4.5 倍长
   （`list_ui_elements` 上限 150，真实应用轻易 80+）。元素指针头要在 84 个候选里选，
   而它只见过 14 个候选的世界。
2. **置信度头是诚实的**：真实域升级率 90%，也就是"它知道自己不知道"，没有乱点——
   升级协议按设计工作（这也解释了 2026-09-19 真实冒烟时"主动低置信升级"）。
3. **但"必然升级还要白问一次"是纯亏**：每步白花 0.45s。于是加了**训练分布门控**
   （`jev_bridge.ood_check`）：元素数 > 训练集最大值（25）时不问模型，直接升级。

   门控效果（`calibration.json` 新增 `train_stats`）：

   | 域 | 门控前 | 门控后 |
   |---|---|---|
   | 真实域 升级率 / Jev 耗时 | 0.90 / 452 ms·步 | **1.00 / 0 ms·步** |
   | mock 域 覆盖率 / 升级率 | 0.763 / 0.237 | **0.763 / 0.237（不变）** |

   阈值取训练集**最大值**而不是 p95：只有训练时真没见过的尺度才拦，分布内长尾仍交给置信度头，
   不重复收税。

**负面结果（省掉一次弯路）**：想用"关键词短名单"把 84 个元素压到 20 个，
在真实域**不可行**——真实 goal 不引用元素名（"78 乘以 9" vs 按钮 `Multiply by`），
按关键词打分排序后 gold 元素排名中位 **36**，recall@10 = **0%**、@30 = 29%、@50 = 61%；
而 mock 域 recall@10 = 99.7%（因为 mock goal 直接引用名字「保存」）。
→ **压缩只能靠学出来的检索器，不能靠字符串匹配**；顺带说明 mock 的 goal 措辞过于"照抄元素名"，
本身就是要修的分布偏差。

## 8. 诚实边界

1. **VLM 侧样本只有 10 步**（按 API 预算抽的 4 个回合）。它的时延量级稳（p50 6.0 s），
   准确率数字噪声大，不能当结论用。
2. **VLM 看的是合成底图**（灰白窗口 + 控件名文字），编号框用的是线上同一份 `som.annotate`，
   prompt 与 `VisualLoop` 逐字符一致。合成底图让 VLM 吃亏，不影响 Jev（它不看图）。
3. **观测/执行成本是「本机实测 + 常量」**：UIA 枚举 0.68 s 是在 owner 当前桌面（多窗口）实测的；
   执行 0.18 s/步是 mock UIA Invoke 的常量，两个驾驶者同值、在对比中抵消。
   真实 mock 窗口里的 UIA 枚举通常更快。
4. **这不是真 GUI 端到端**（无头 replay）。真 GUI 需要开窗，按约束只能 owner 离开时跑：
   `scripts/bench_gui.py --allow-gui --driver {oracle,jev,vlm}` 已备好（零鼠标执行器 + 真
   `VisualLoop`），代码路径已用 `--offscreen` 自检（窗口/截图/标注/动作分发/清理都能跑通），
   但**真窗口 + 真 UIA 那条路没跑过**——首次运行建议人在旁边。
5. **R4 校准漂移仍未验证**：`traces_full` 的 105 步真实轨迹在 `iter_samples` 里几乎全被
   过滤（hotkey/press 不在动作集内），所以部署侧 coverage 只在 mock 域上量过。
6. **SCROLL/WAIT 没有载荷**（v0 动作集只有 8 类，无格数/秒数头）→ 快路径用默认值
   （滚动 -3、等待 1s），属已知精度损失；mock 里 scroll 步占比低，首测影响小。
7. **图标控件没有文字**（owner 2026-09-19 提醒后实测）：真实轨迹里 **11% 的元素 Name 为空**
   （全是 `ButtonControl`——toolbar/窗口按钮这类只有图标的控件），而 **gold 目标里 0 个无名**
   （VLM 也只敢点图例里有名字的）。mock v2 是 **0% 无名**，等于教模型"每个控件都有名字"。
   v3 已按同量级掺入无名图标按钮（实测观测表无名占比 13%），并加验收测试。
   仍未覆盖的部分：**纯图标语义**（图标含义只在像素里，UIA 完全没名字）——Jev 只能靠位置/类型
   推断，VLM 靠 SoM 编号能点但说不清语义；这属于 R5（UIA 盲区）的一个子集。
8. **多窗口配额**：元素表上限 150，前台窗口拿一半、其余窗口均分另一半 —— 也就是说
   **后台窗口的控件随时可能被配额切掉**（实测 mock 窗口作为后台窗口时 85 个控件只剩 25 个）。
   真实多窗口任务（"去另一个窗口点确认"）会撞上这个上限，v1 要重新设计配额策略。
9. **BLOCKED 会提前结束任务**：mock 首测里认输 0 次（命中 0、误认输 0），
   但真实桌面冒烟时 Jev 曾主动低置信升级——认输的假阳性代价需要更多真实数据才能估。
10. **真实域数字是"乐观口径"**（2026-09-19 复核发现）：§7 那张表的 real 行，
    评估集 `traces_full` **本身就在训练数据里**（v0 当年就是 mock v1+v2+真实 一起训的）。
    所以 0.17 这个数已经是"见过这批真实数据"之后的成绩，真·零样本只会更低。
    **好消息是它不破坏 A/B**：两轮训练都含同一份真实数据、评估集也相同，
    mock 分布是唯一变量，所以"v0 → v3 有没有动"仍然可信，**只有绝对值不能对外引用**。
    想要干净数就训练时不喂 `traces_full`，再拿它当零样本测试集。

## 9. 下一步建议（按性价比）

1. **补数据分布（当前第一优先级，见 §7）**：
   - mock v3：窗口 40–120 元素（现在 14）、goal **不引用元素名**、中英同义词对
     （乘以/×/Multiply by、等于/Equals、保存/Save）——目标是把训练分布搬到真实尺度和语义上；
   - 真实轨迹 up-weight（TRAINING §5 的 SFT-B：真实占比 ≥70%），并继续攒真实数据。
